# v1 稳定性与发布规划

最后维护：2026-10-14

状态：实施中。起点为提交 `29c27a0`；相机取消、所有权和异常启动修复已完成本地主机与压缩产物门禁，模拟器设备矩阵部分完成；真机、完整恢复矩阵、正式签名与分发仍未完成。当前证据集中维护在任务清单，不由计划状态推断设备通过。

## 目标与已有基础

下一阶段目标是完成相机生命周期、异常恢复和正式产物验收，使 v1 在明确的实测环境中达到可发布状态。当前先收敛自检及后台切换时的相机释放与取消链路，再按阶段退出条件推进。

API 102 双入口、中文简介、品牌图标和 APK 静态门禁已交付。用户确认 GazeKeep 1.1.0（2）在模拟器与 Xiaomi 12 Pro 上，模块显示/API 102 识别、重启后桥接、注视保亮与转头/看不清后熄屏、隐私指示器功能、覆盖升级与配置保留均人工通过。具体证据和缺项以[任务清单与验证](todo.md)为准；这些结果不代替后续修改版本、其他 ROM、legacy 独立环境或本地压缩 Release 的验收。

本阶段范围包括采集取消、资源所有权、系统熄屏恢复、三后端异常路径、相关页面回归和发布准备。MediaPipe、暗光增强、新后端、网站和自动化 UI 框架留待后续独立规划。本轮稳定性候选为 1.1.2（versionCode=4），压缩运行验证先使用开发签名副本；正式签名及对应实际 APK 验收仍需完成。

## 执行原则

- 生命周期与异常实现遵循[运行架构](../architecture/android-runtime.md)、[采集架构](../architecture/capture-classification.md)和[决策架构](../architecture/engine.md)；若需要改变设计，先更新命中的活动架构，再同步实现与调用方。
- 使用[测试规范](../development/testing.md)的七条不变量与设备矩阵。可隔离缺陷先建立失败测试；硬件问题先定义并复现场景，记录版本、前提与结果。
- 保持 Unknown、取消和链路失败不保亮，保亮上限到点必须熄一次；遵循[隐私与安全](../product/privacy-security.md)，不保存图像、人脸特征或原始系统转储。
- 主机、页面、真实完整旅程与 APK 静态检查分别记录。已有测试按受影响行为扩展，不为文档建立新测试框架，也不以 fake 代替设备结果。
- 设备安装、重启、权限和系统配置变更执行前核对当次授权与恢复方法；正式签名材料留在本地。本计划本身不执行设备操作或发布。

## 前置准备：固定验收环境

先补齐 Xiaomi 12 Pro 的当前 Android/ROM、LSPosed 版本和测试 APK 标识，以及两台设备的系统超时、作用域和实际命中候选。设备按相机、传感器及后端能力分配场景；缺少能力的场景记未执行，另选满足条件的环境补证。

每轮记录代码提交、版本/versionCode、APK SHA-256、签名类型、设备/ROM/Android、后端/框架版本、系统超时、提前量、保亮上限、白名单和权限状态。确认目标应用本身没有持续保亮，再开始熄屏测试。

退出条件：每个设备场景可以对应到明确二进制与前提；无法补齐的旧反馈仍保留原有证据边界，不反推环境信息。

## 阶段一：相机生命周期与取消链路

### 核查与实施

当前入口为 `MainActivity.onPause` → `AndroidGazeKeepController.pauseSelfTest` → `SelfTestCoordinator.pause`；离页与 controller 关闭也有取消入口。实现已改为主线程绑定、解绑并等待清理交接，预览销毁只清除 surface；进程共享协调器隔离自检与服务采集。主机回归已覆盖旧状态、迟到结果和排队采集取消缺陷；Home 的硬件释放基线与其他设备操作仍按实际 APK 分别补证。

1. 复现待办中的 Home 场景，区分取消请求、采集结束、解绑执行、相机客户端消失及状态栏指示器消失；指示器显示时长不能单独证明相机仍占用。
2. 核查等待 provider、绑定前、预热、分类中、清理投递中发生取消或关闭的路径；确认旧结果不推进自检或影响新会话。
3. 核查自检与服务采集共享 `ProcessCameraProvider` 时的所有权、避让和 `unbindAll` 影响，防止旧清理关闭新采集，也防止后台重复绑定。
4. 按复现证据修复受影响路径，保持取消传播、每帧关闭、资源清理可重复调用。页面取消不意外关闭已启用的应用服务；异常通知和状态说明保持一致。

主要入口与现有测试：

| 范围            | 实现入口                                                                  | 回归入口                                                     |
| --------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------ |
| 自检与 Activity | `android` 的 MainActivity、SelfTestCoordinator、AndroidGazeKeepController | SelfTestCoordinatorTest、页面设备场景                        |
| 采集与清理      | `engine` 的 CameraXFrameSource、AttentionCaptureSession                   | AttentionCaptureSessionTest、FrameAnalysisTest、真实相机场景 |
| 服务与自检避让  | `android` 的 BackendSession；`shared` 的自检导航与预览契约                | 相关会话测试与运行中自检旅程                                 |

### 设备验收

| 场景与步骤                                   | 预期与证据                                                       |
| -------------------------------------------- | ---------------------------------------------------------------- |
| 自检采集中按 Home、返回、取消或关闭 Activity | 本轮取消、相机释放、不提交迟到结果；记录取消至实际释放耗时       |
| 自检期间旋转、离页后再进入、快速重复操作     | 不重复占用，不让旧清理破坏新会话；两步自检可重新完成             |
| 等待相机或采集中撤销权限                     | 中止并释放，状态可解释，不误记自检通过；重新授权后可恢复         |
| 服务已运行时进入自检，再取消自检             | 服务检测避让自检，自检结束后按配置恢复；无重叠占用或误关闭总开关 |
| 采集前及采集中打开系统相机或扫码             | 让出摄像头，不崩溃、不保亮；其他应用正常使用，结束后可再次检测   |

先测量目标设备的释放基线，再依据相机可再次使用、取消时序和现有采集截止核对可接受范围；如需新增明确的释放时限，先在采集架构定义并配套测试，不把当前 1600 ms 采集预算当作释放预算。

退出条件：目标设备上的上述场景有实际结果，已复现的资源残留、迟到结果或跨会话清理缺陷已修复并回归；未复现问题记录条件与观察，不标成已修复。

## 阶段二：保亮上限与异常恢复

阶段一通过后，在同一候选 APK 上连接真实组件验证下表。公共决策覆盖三后端，后端专属场景在满足条件的设备上独立执行；测试前保存临时配置，结束后恢复并核对。

| 范围           | 可复现场景                                                                 | 验收标准                                                                           |
| -------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 连续注视与上限 | 短系统超时、1 分钟保亮上限，持续注视至上限，再真实触摸                     | 自身 Extend 不重置累计；到点实际熄一次；真实触摸后可开启新一轮                     |
| 触摸与息屏     | 采帧期间真实触摸；采集中手动息屏再亮屏                                     | 本轮取消且不 Extend；息屏期间无采帧，下一次亮屏按正常状态恢复                      |
| Unknown 与门控 | 暗光、多脸、口袋、朝下；视频自身保亮和通话                                 | Unknown 不保亮；已具备的门控休眠，系统相机和系统保亮策略不受干扰                   |
| 服务与后端     | 后端切换、掉线、关闭无障碍、划掉任务及服务被杀                             | 切换期不 Extend，无 Hold 残留；按后端恢复语义回到系统熄屏，异常说明/通知可观察     |
| 无障碍 Hold    | 达上限、Unknown、关闭服务及重新连接                                        | 窗口/常亮锁释放，设备实际熄屏；旧服务销毁不破坏新连接                              |
| Shizuku 恢复   | 触发临时超时退路后息屏、服务销毁、Binder 断开/重连或 Shizuku 重启          | 原值先持久化；可连接时写回并读回确认，再清记录；离线时保留待恢复状态，重连后恢复   |
| LSPosed 桥接   | 旧 seq、禁用系统作用域和重新启用；错误签名以隔离测试或有恢复方案的环境验证 | 过期请求不调用 userActivity；不就绪时不保亮；系统启动正常，恢复后桥接状态准确      |
| 隐私指示器     | 实验开关关闭/开启/关闭、切换后端、自检及后台采样、其他应用用相机           | 默认指示器保留；过滤仅影响自身摄像头活跃通知，关闭或条件失效恢复，其他应用不受影响 |

具体恢复实现遵循[无障碍架构](../architecture/backends/a11y.md)、[Shizuku 架构](../architecture/backends/shizuku.md)与[LSPosed 架构](../architecture/backends/lsposed.md)。Binder 离线时不能将“记录仍在”写成“系统超时已恢复”，必须记录残留与恢复结果。

退出条件：七条不变量在受影响逻辑上通过，三后端关键真实恢复旅程完成，异常不会留下持续保亮、相机占用或未说明的系统设置残留。legacy 使用确实选择旧登记的独立环境回归；没有条件时保留未测声明，不宣称通过。

## 阶段三：正式 Release 与交付

1. 对已收敛的候选版本执行完整主机门禁、应用构建/lint、架构检查和文档检查。核对最终运行依赖、许可及 APK 权限与注册元数据。
2. 准备正式签名的 R8/资源压缩 Release，记录提交、版本、SHA-256 与签名身份。开发签名副本只能作为明确标注的压缩运行验证，unsigned APK 不作为分发产物。
3. 对实际签名产物执行 APK 门禁，并在具备条件的设备上重跑核心旅程：安装/覆盖升级、配置保留、自检与启用、后台/重启、真实注视与熄屏、资源释放及后端异常恢复。
4. 完成页面回归：导航/返回/旋转、明暗与大字体、应用列表空结果和失败重试、日志卡片/分享/导出时间一致、配置冷启动回读及快速开关。
5. 按[发布门禁](../development/release.md)在任务清单整理实测环境、框架版本、命中候选、已知限制与未测范围，发布说明只写更新日志与启用步骤。形成可审查的本地产物和发布说明后，再依据发布授权进行分发。

升级测试先确认签名兼容；不能为完成测试卸载用户应用或清空数据。若候选代码、签名或 APK 发生变化，重新标识产物并重跑受影响验收，不沿用其他二进制的通过记录。

退出条件：拟分发的实际 APK 有对应签名、静态门禁和设备证据，发布声明与实际支持范围一致；不存在下面列出的阻断项。

## 阻断项与证据要求

Unknown/失败仍保亮、到上限不熄屏、相机无法释放或让出、取消后旧结果生效、系统进程异常、Shizuku 恢复条件具备时仍残留临时超时、隐私指示器影响其他应用、图像/敏感数据落盘、签名或升级造成配置丢失，均阻断候选发布。

未经验证的 ROM、后端或 legacy 环境继续列为未测；若属于拟声明支持范围，必须补验收。不能把缺条件从矩阵中删掉以满足退出条件。

每条设备记录包含场景 ID、前提、步骤、预期、实际、通过/失败/未执行、结果来源、清理结果与必要的耗时/计数。相机释放证据只保留所需脱敏状态字段与时间；不保存人脸截图、特征、序列号或原始 dump。当前结果集中维护在[任务清单](todo.md)，本计划不累积执行流水。

## 验证入口与实施顺序

每次实施先按目标路径读取目录规则。相机与自检修改通常运行 `:engine:testDebugUnitTest`、`:android:testDebugUnitTest` 及应用 Debug 构建/lint；涉及 reducer、shared 或后端时增加对应模块门禁。正式候选使用 `pnpm --filter @gazekeep/app verify` 完整主机入口，并按[测试规范](../development/testing.md)补设备证据。

```bash
pnpm verify:architecture
pnpm verify:docs
pnpm verify:agent-assets
pnpm verify:apk --apk <实际验收APK路径>
git diff --check
```

执行顺序：固定环境 → 阶段一复现与修复 → 阶段二恢复矩阵 → 阶段三签名产物验收。各阶段的实现、测试和活动架构保持同步，发现缺陷按实际根因限定修复范围。本轮门禁、实际设备结果和未执行条件以任务清单为准；开发签名压缩副本不代表正式发布产物。
