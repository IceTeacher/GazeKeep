# 单条提交信息

为全部暂存变更生成一条符合仓库规范的提交信息。只请求生成信息时，输出即完成，不修改索引或提交。

## 依据与输出

- 读取 `scripts/repo-tools/config/commitlint.config.ts` 的当前类型、范围与 emoji 选项，近期非合并提交仅作措辞参考，不沿用仅为历史兼容保留的值。
- 以 `git diff --cached` 为依据，结合状态和文件清单判断范围；需要文件内容时读取索引版本。未暂存和未跟踪内容不纳入，空索引明确报告无暂存变更。
- 标题使用 `type(scope): emoji 中文描述`，概括主要行为或结果。中文描述采用“动词 + 名词 + 效果 / 目的 / 解决的问题”结构，推荐以 `新增`、`修复`、`优化` 等动词开头，明确改动对象与达成效果（例如：`fix(web): 🐛 修复官网项目的模拟手机展示区域无法正常渲染的问题`、`feat(android): ✨ 新增APP的ABI分架构打包功能`、`chore(ci-cd): 🔨 优化流水线运行逻辑以复用已验证提交`），避免使用缺少动词动作或效果的空泛短语。复杂变更按需补充正文，说明相关修复、接口或验证事实，不规定条数，不推测未验证结果。
- 用 `pnpm exec commitlint --config scripts/repo-tools/config/commitlint.config.ts` 校验候选标题；失败修正后重验，工具缺失如实报告。

输出可直接使用的提交信息；必要时用一句话解释语义。不要用文件名清单代替描述。

## 已授权提交时

只生成说明无需执行此分支。用户明确要求提交时，遵循[代理工作流](../../workflow.md#提交说明)：

- 生成提案时记录 HEAD 和 `git diff --cached --binary` 的摘要，提交前复核。快照变化则重新分析、校验；若影响用户批准的具体方案，先更新方案并确认。
- 授权仍适用且快照一致时，直接提交暂存内容，不先 `git add`，不推送。修订措辞不撤销已有提交授权，除非用户要求再次审阅。
- Hook 失败先核对原因与索引状态；只修复本次授权范围内的问题，复核后重试。索引恢复冲突或影响范围不明时保留现场并报告。
