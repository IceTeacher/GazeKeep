# 分组提交信息

分析当前暂存区，提出语义清晰、范围明确、依赖顺序合理的提交分组和对应标题。生成阶段只读，不更改暂存区，也不提交。

## 分析与分组

1. 在仓库根目录读取 `scripts/repo-tools/config/commitlint.config.cjs`、根 `AGENTS.md` 和与变更相关的目录规则；查看最近 8 条非合并提交标题（`git log -8 --no-merges --format=%s`）。配置决定允许的类型、范围和 emoji 映射；历史仅用于参考语义、范围选择和中文措辞风格。
2. 用 `git status --short --branch`、`git diff --cached --stat`、`git diff --cached --name-status` 和 `git diff --cached` 分析暂存内容。不要把未暂存或未跟踪的改动算进分组。需要读取某个已暂存文件的准确内容时，读取索引版本，不要依赖含有额外未暂存编辑的工作区版本。
3. 暂存区为空时，明确报告没有可分组的暂存变更；不要回退到未暂存内容。
4. 按业务行为、修复目标、契约边界和依赖关系划分尽可能少的独立提交组。不得拆分单个文件中的 hunk；每个变更文件只能属于一组。重命名的源路径和目标路径必须留在同一组。遵循仓库规则，将必须同步的契约、生成物、迁移、实现和测试留在适当的同一组。
5. 每组应能独立解释其目的。不要为了凑出多个提交而拆分强耦合的改动；若整体更适合作为一个提交，就说明理由并只给出一条标题。
6. 按依赖关系确定提交顺序，不按目录或文件名机械排序。每组标题应概括该组的语义，不复用同一泛化描述。
7. 每条标题使用 `type(scope): emoji 中文描述`。类型与范围优先采用 `scripts/repo-tools/config/commitlint.config.cjs` 当前交互选项中的值，不要照搬仅为历史兼容而保留的类型或范围。逐条在仓库根目录用 `pnpm exec commitlint --config scripts/repo-tools/config/commitlint.config.cjs` 校验；失败时修正并重验。若工具不可用，说明未能验证。
8. 根据每个提交组的变更规模决定说明深度：
    - 单一文件、单一行为且边界清楚的组只给标题。
    - 跨多个模块，或同时包含契约、迁移、生成物、实现、测试、任务记录中的多项，或一个组内有多个相互关联的修复点时，在标题下增加 2～5 条正文说明。每条使用 `- ` 开头，先标明子系统或改动面，再说明关键实现、行为结果或验证覆盖；不要用文件名清单替代说明。
    - 正文按“用户可见结果/根因修复 → 关键实现或边界 → 测试、验收、错误收敛或恢复语义”的顺序组织，只陈述从暂存区确认的事实。

## 提交边界

- 展示完整分组、每组的文件清单、简短理由、顺序和标题，然后等待用户对整组方案的一次确认。展示阶段不得运行 `git add`、重置暂存区或 `git commit`。
- 只有用户在生成前明确要求“生成后直接提交”时，才可以省略后续确认；仍须先生成并校验全部标题。
- 提案时记录 HEAD 和暂存差异摘要。确认后先复核提案所依据的 HEAD 和暂存内容；若状态变化，停止提交，按最新暂存内容重新分组并重新确认。
- 分组提交前检查每组路径是否存在未暂存差异。由于按文件分组，若某个已暂存路径同时含有未暂存编辑，不得用工作区版本覆盖暂存版本，也不得重置或重新暂存来冒险拆分；停止提交并说明需要先消除该路径上的状态歧义。
- 通过预检后，按提案顺序逐组执行本地提交，每次只提交该组明确列出的路径，并确认该操作不会带入其他暂存或未暂存改动。提交钩子失败或出现意外状态时立即停止；报告已成功提交的组和未完成的组，不推送。
- 用户要求修改任一分组或标题时，重新展示完整最终方案；修改后的方案需再次整组确认。

## 输出

```text
建议分为 N 组：

1. <分组目的与顺序理由>
   文件：
   - <路径>
   提交信息：
   <type(scope): emoji 中文描述>
   - <子系统或改动面：关键实现与行为结果>
   - <错误处理、测试或任务记录：验证覆盖与收敛结果>

2. ...
```

简单提交组省略标题下的正文条目；较大提交组必须给出 2～5 条能解释行为、实现和验证的正文说明。每个暂存变更路径必须且只能出现在一个组中。不要声称已提交，除非所有已报告为成功的提交实际完成。
